You can manage {admc-name} Helm chart,
like other Helm charts, with
https://documentation.suse.com/cloudnative/continuous-delivery/latest/en/index.html[SUSE
Rancher Prime: Continuous Delivery] (Rancher Fleet).
Rancher Fleet uses Kubernetes CRDs
to define a GitOps approach to managing Kubernetes clusters.
It does this by defining
https://documentation.suse.com/cloudnative/continuous-delivery/latest/en/explanations/concepts.html[Fleet
Bundles].

[#_installing]
== Installing

The {admc-short-name} chart is a standard chart. See the
xref:/quick-start.adoc[Quickstart docs] for more information.

The {admc-short-name} Helm chart and its container images are distributed
through the https://apps.rancher.io[SUSE Application Collection]. To install
{admc-short-name} with Fleet, Fleet needs credentials to pull the chart, and the
target clusters need credentials to pull the container images. See the
https://docs.apps.rancher.io/get-started/authentication/[Application Collection
authentication documentation] for how to obtain them.

. On each target cluster, create the `{admc-namespace}` namespace and an image
  pull secret, so the cluster can pull the {admc-short-name} container images:
+
[subs="+attributes",console]
----
kubectl create namespace {admc-namespace}

kubectl create secret docker-registry application-collection \
  --namespace {admc-namespace} \
  --docker-server=dp.apps.rancher.io \
  --docker-username=<your-username> \
  --docker-password=<your-token>
----

. On the Fleet management cluster, create a Secret with the Application
  Collection credentials in the namespace of the `GitRepo`. Fleet uses it to pull
  the Helm chart. This example uses the `fleet-local` namespace, which targets
  the local cluster; use `fleet-default` to target downstream clusters:
+
[subs="+attributes",console]
----
kubectl create secret generic application-collection-helm \
  --namespace fleet-local \
  --from-literal=username=<your-username> \
  --from-literal=password=<your-token>
----

. In your Git repository, add a `fleet.yaml` file that deploys the
  `suse-security-admission-controller` chart from the Application Collection, in
  a directory such as `admission-controller`:
+
[subs="+attributes",yaml]
----
defaultNamespace: {admc-namespace}
helm:
  releaseName: {admc-release}
  repo: {admc-chart-location}
  version: 1.1.0
  values:
    global:
      imagePullSecrets:
        - application-collection
----
+
Add your own chart values under `helm.values`.

. Create a `GitRepo` that watches that directory. The `helmSecretName` field
  references the Secret with the Application Collection credentials. Fleet
  forwards those credentials only to the Helm repositories that match
  `helmRepoURLRegex`:
+
[subs="+attributes",yaml]
----
kubectl apply -f - <<EOF
apiVersion: fleet.cattle.io/v1alpha1
kind: GitRepo
metadata:
  name: {admc-release}
  namespace: fleet-local
spec:
  repo: <your-git-repository-url>
  branch: main
  paths:
    - admission-controller
  helmSecretName: application-collection-helm
  helmRepoURLRegex: "^oci://dp.apps.rancher.io/"
EOF
----

. Check that Fleet deployed the bundle:
+
[subs="+attributes",console]
----
kubectl get gitrepo -n fleet-local {admc-release}
kubectl get pods -n {admc-namespace}
----

Fleet deploys the chart with Helm against the target cluster, so the
certificates that the chart creates on installation are reused on later
deployments. Unlike with ArgoCD, no configuration is needed to ignore
differences in the certificate Secrets or the webhook configurations.

See the
https://documentation.suse.com/cloudnative/continuous-delivery/latest/en/how-tos-for-users/gitrepo-add.html[Continuous
Delivery documentation] for more information about `GitRepo` resources and
credentials.

== Removing

Removing the {admc-short-name} chart will leave around the user-managed custom
resources and CRDs. See the xref:/quick-start.adoc[Quickstart docs] for more
information.

{admc-short-name} Kubewarden uses a pre-delete helm hook job in
`suse-security-admission-controller` chart that deletes the controller, webhooks, resources
that enable PolicyServers to process policies, default PolicyServer and
recommended policies.

Uninstalling CRDs automatically isn't normally supported by any tooling, and
Rancher Fleet is no exception.

To manually remove the CRDs and any remaining user-managed custom resources
after removing the Fleet Bundle:

* Remove the {admc-short-name} Bundle from your Fleet Git repository, or
  delete it directly with `kubectl delete bundle`, and let Fleet reconcile the
  removal of the Helm release from the target clusters.
* Confirm the Helm release is uninstalled and the pre-delete hook completed,
  by checking that the `{admc-release}-ssac` Deployment and webhooks are
  gone from the targeted clusters.
* Manually delete the remaining CRDs, which will also remove the user-managed
  custom resources on each targeted cluster:
+
[subs="+attributes",console]
----
kubectl delete crd policyservers.policies.kubewarden.io
kubectl delete crd clusteradmissionpolicies.policies.kubewarden.io
kubectl delete crd admissionpolicies.policies.kubewarden.io
kubectl delete crd clusteradmissionpolicygroups.policies.kubewarden.io
kubectl delete crd admissionpolicygroups.policies.kubewarden.io
----
+
If no other tool in the cluster uses the OpenReports CRDs, also delete the
ones installed by the chart:
+
[subs="+attributes",console]
----
kubectl delete crd reports.openreports.io
kubectl delete crd clusterreports.openreports.io
----
+
[NOTE]
====

Because Fleet's `GitRepo`/`Bundle` resources target multiple clusters, you
need to repeat this manual CRD cleanup on every downstream cluster where the
Bundle deployed {admc-short-name}.

====
